CardFit / Technical Planning Briefing

마이데이터에서
사용자 카드 조합까지

이 문서는 개발 미팅에서 CardFit의 기술 선택과 제품 흐름을 한 번에 설명하기 위한 브리핑 문서입니다. 비즈니스 로직은 어떤 데이터로 어떤 판단을 내리는지, 딜리버리 로직은 그 판단을 어떤 화면·서버·데이터·배포 계층으로 사용자에게 전달하는지를 설명합니다.

핵심 스토리마이데이터는 현재 카드 상태의 원천 입력이고, 사용자는 앞으로의 지출 계획으로 분석 의도를 보완합니다. CardFit은 서버에서 결정론적으로 분석·추천하고, 사용자의 확정과 행동을 기록한 뒤, 카드사에서 실제로 바뀐 상태를 다음 동기화에서 다시 읽어 추천과 대조합니다.
범위 선언현재 v0.1은 실제 마이데이터 API·인증·카드 발급/해지를 구현하지 않고 Prisma Seed Mock으로 흐름을 검증합니다. 아래 문서에서 현재 구현과 실연동 확장 설계를 구분해 표시합니다.

1. 우리가 선택한 기술 스택

기술 이름을 나열하는 것이 아니라, 각 기술이 어떤 책임을 맡는지로 설명합니다.

앱·프레임워크
Next.js App Router

화면 경로와 서버 처리를 한 애플리케이션에서 구성합니다. TypeScript로 데이터 계약과 도메인 타입을 고정합니다.

UI
Tailwind CSS
+ shadcn/ui

모바일 402×874와 데스크톱을 같은 토큰·컴포넌트로 구현합니다. 상태 배지·카드·CTA를 재사용합니다.

데이터
Prisma
+ Supabase PostgreSQL

HeldCard·PastSpend·Calculation 등 정본 데이터를 저장합니다. 로컬은 Supabase CLI, 배포는 Supabase PostgreSQL을 사용합니다.

계산
Server Actions
+ Rule Engine

DB 접근과 계산을 서버에서 실행합니다. 혜택 금액과 게이팅은 AI가 아닌 결정론적 규칙 엔진이 담당합니다.

외부 데이터
MyData Adapter
(v1 확장)

외부 API의 인증·필드명·분류 차이를 내부 Repository 경계 뒤에 숨깁니다. v0.1에서는 Fixture Repository로 대체합니다.

배포
Vercel

Git Push 기반 Preview·Production 배포를 사용합니다. 서버 환경변수와 공개 변수를 분리합니다.

실행 경계
카드사 공식 채널

신규 발급·해지는 CardFit이 대행하지 않습니다. 사용자가 카드사에서 직접 실행하고 CardFit은 다음 동기화에서 결과를 확인합니다.

사용하지 않음
AI 계산·공개 REST API

금융 계산은 AI를 사용하지 않습니다. MVP에는 별도 백엔드 서버나 공개 REST API를 만들지 않습니다.

관련 제약: C-TEC-001~004, C-TEC-007 수용 · C-TEC-005 Vercel AI SDK는 현재 AI 미사용으로 기각

5. 사용자 여정으로 스토리텔링하기

“어떤 일이 일어나는가”와 “어느 계층에서 일어나는가”를 한 단계씩 연결합니다.

1
수집

지금 어떤 카드와 소비 패턴을 가지고 있는가?

v0.1에서는 getMockData() Server Action이 Prisma Seed에서 HeldCard·PastSpend·BenefitRule을 읽습니다. v1에서는 같은 호출 경계 뒤에 MyData Adapter를 꽂아 인증·동의 범위·기준일을 확인합니다.

2
정규화

외부 데이터의 차이를 도메인 모델 뒤로 숨긴다.

MyData 제공자마다 카드 식별자, 거래 분류, 날짜, 혜택 필드가 다를 수 있습니다. Adapter가 이를 CardFit 내부의 HeldCard·PastSpend·BenefitRule로 변환하므로 화면과 Rule Engine은 특정 Provider에 직접 의존하지 않습니다.

3
확인

과거 패턴을 미래 지출 계획의 초안으로 제시한다.

과거 12개월 소비는 사용자의 의도를 대신하지 않고 입력 초기값을 채우는 재료입니다. 사용자가 카테고리·추가 지출 금액·실제 지출 기간을 확인한 값만 FutureSpendPlan.confirmed=true로 저장하고 계산에 사용합니다. 감소 방향은 입력받지 않습니다.

4
분석

세 가지 미래 시나리오에서 카드 조합의 순혜택을 계산한다.

calculatePlan() Server Action이 확인된 미래 계획, 카드, 규칙, 제약을 받아 후보를 생성합니다. 계산은 결정론적이어야 하며 같은 입력은 같은 결과를 반환해야 합니다.

Net Benefit = Gross Benefit − (연회비 + 실적 재적립 손실 + 발급 대기 비용)
변경 제안 = Net Benefit ≥ 50,000원 AND Net Benefit ≥ Gross Benefit × 15%하나라도 미달하면 후보 변경이 아니라 모든 보유 카드 유지(KEEP)를 정상 결과로 반환합니다.
5
추천

추천의 품질은 많이 제안하는 것이 아니라, 제안하지 않을 때를 아는 것이다.

통과한 후보만 신규·유지·정리 상태와 카드별 Allocation을 반환합니다. 근거 6항목이 부족한 카드는 후보에서 제외하고, 후보가 없으면 현재 조합 유지로 폴백합니다. 금액과 근거 설명은 AI가 아니라 규칙과 고정 템플릿으로 만듭니다.

6
선택·기록

사용자는 결과를 검토하고 조합을 확정한다.

근거 화면의 CTA를 통해 변경안 또는 현재 조합 유지를 확정합니다. confirmPlan(candidateId)가 확정 시점의 금액·기준일·rule_version을 동결하고, ClientEvent에는 결과열람·근거열람·조합확정·아웃링크클릭을 기록합니다.

7
외부 실행

실행은 카드사, CardFit은 다음 행동의 경계를 알려준다.

신규 카드만 카드사의 공식 페이지로 이동합니다. 신청·심사·해지 제출은 하지 않습니다. 사용자가 카드사에서 실제 행동을 수행했다는 사실과 CardFit의 “확정 의향”은 서로 다른 상태로 관리해야 합니다.

8
재동기화

다음 MyData 동기화에서 실제 카드 상태를 다시 확인한다.

사용자 실행 이후 MyData를 다시 읽어 현재 보유 카드·거래·상태를 Adapter로 정규화하고, 이전 확정 조합과 대조합니다. 새 카드가 생겼는지, 기존 카드가 사라졌는지, 추천 당시의 기준일·규칙이 오래됐는지 판정합니다. 오래된 결론은 자동 실행하지 않고 재계산 또는 재확인을 요구합니다.

Provider API 실패·부분 성공동기화 시각과 수집 범위 표시재시도 또는 이전 데이터 사용 여부 선택정책 확정 전 금지
지금 결정하지 않는 것동기화 트리거(Webhook/주기/재진입), 최신성 기준, 부분 성공 정책, cursor와 중복 처리 방식, 토큰 만료·철회 처리는 MVP의 구현·완료 조건에 넣지 않습니다. 실제 Provider와 연동 범위가 정해지는 v1 착수 시 별도 설계·결정합니다.

8. 상태·오류·보안의 최소 계약

핵심 상태

정상 결과만 정의하면 안 된다.

  • Empty: 미래 지출 0건, 계산 차단
  • Calculating: 계산 중 중복 요청 방지
  • Success: 근거 6개 충족, 결과 공개
  • Keep: 임계 미달 또는 제약 과다
  • Evidence Incomplete: 근거 보완 전 결과·CTA 차단
  • Stale/Expired: 다시 계산 또는 재확인
오류·보안

실패를 조용히 성공으로 바꾸지 않는다.

  • 오류마다 code, message, retryable, missing을 분리
  • Server Action과 Adapter에서 멱등 키로 중복 저장·중복 동기화 방지
  • DB 자격증명·Provider token은 서버 환경변수와 서버 실행 영역에만 보관
  • NEXT_PUBLIC_에는 공개 가능한 값만 둠
  • 개인정보 보존 기간·삭제 방식·동의 철회는 실연동 전 결정
