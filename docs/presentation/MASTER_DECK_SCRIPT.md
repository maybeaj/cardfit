## 슬라이드 2 — 문제 정의 & Why Now

**배점 매칭:** 문제·목표·범위와 기획 자산 재사용 — **15점**

**화면 구성 제안:** 좌우 대비 레이아웃. 왼쪽 "기존 카드 추천"(지난 1년 소비 → 카드 한 장 비교 → 발급 연결), 오른쪽 "CardFit"(현재 소비 확인 → 앞으로 쓸 돈 입력 → 카드 조합 재계산 → 근거 확인 → 카드사 연결). 하단에 "직접 확인한 경쟁 5곳 중 미래 소비를 반영하는 곳 0곳" 수치 배지.

**핵심 내용 요약:**
- 문제: 소비는 곧 바뀌는데 추천은 지난 소비만 본다
- 근거: 카드 실적구간·한도·연회비·제외조건의 복잡성이 소비자 결정 피로를 만든다
- 차별점: 시간축(과거→미래)과 조합축(카드 한 장→조합) 두 가지를 동시에 바꿈

**발표 대본:**
> 카드 추천 서비스는 이미 많습니다. 그런데 저희가 직접 확인한 5개 경쟁 서비스 중 단 한 곳도 "앞으로 쓸 돈"을 반영하지 않았습니다. 전부 지난 1년 소비를 보고 카드 한 장을 추천하죠. 하지만 혼인이나 이사를 앞둔 사람에게 중요한 건 지난달 커피값이 아니라, 다음 달에 나갈 혼수 비용, 예식 비용입니다. 게다가 카드 혜택은 전월실적 구간, 통합 한도, 연회비, 제외 업종까지 복잡하게 얽혀 있어서 사람이 직접 계산하기 어렵습니다. 이 두 가지 — **미래를 안 본다는 것, 그리고 계산이 너무 복잡하다는 것** — 이 저희가 푸는 문제입니다.

## 슬라이드 3 — 기획 자산 재사용: Copy가 아니라 Curate

**배점 매칭:** 문제·목표·범위와 기획 자산 재사용 — **15점** (2번과 배점 공유, 재사용 근거 파트)

**화면 구성 제안:** 깔때기(funnel) 다이어그램. 상단 "2차 역기획 프로젝트 (11개 방법론 워크북, 32p 덱)" → 중간 "선별 기준: 이번 구현에 근거·결정·제약으로 쓰이는 것만" → 하단 "이번 프로젝트 산출물(KB·SCOPE·PRD·SRS)". `docs/REUSE_MAP.md` 캡처.

**핵심 내용 요약:**
- 2차 프로젝트(`jennie-brain/team-project_2nd`)의 결론을 승계하되, 전부 옮기지 않고 **재사용·폐기·추가확인**으로 판정
- 원칙: "옮기지 않은 것은 링크로만 연결한다"
- 핵심 기능(F-04 Net Benefit 게이팅), 개선축 2개(시간축/조합축), MoSCoW 프레임은 그대로 승계

**발표 대본:**
> 저희는 이번 프로젝트를 맨땅에서 시작하지 않았습니다. 2차 역기획 프로젝트에서 이미 카드 시장을 11개 방법론으로 분석해 뒀고, 그 결론 중 **이번 32시간 구현에 실제로 쓰이는 것만** 골라 가져왔습니다. `REUSE_MAP.md`라는 문서 하나로 "이건 재사용, 이건 폐기, 이건 추가 확인 필요"를 전부 판정했고요. 예를 들어 핵심 기능인 Net Benefit 게이팅 로직은 그대로 승계했지만, 과거·미래 대조 화면처럼 구현 비용 대비 효과가 낮다고 판단한 건 과감히 뺐습니다. 이게 **자산을 베끼는 게 아니라 큐레이션하는 것**이라고 생각합니다.

## 슬라이드 4 — Knowledge Base: 근거 등급까지 관리한 리서치

**배점 매칭:** Knowledge Base와 기획 고도화 리서치 — **15점**

**화면 구성 제안:** `docs/knowledge-base/00-index.md`의 7개 문서 표를 그대로 슬라이드에 캡처(01 제품맥락~07 사업모델). 옆에 "완료 기준: 팀원이 '왜 이 기능이 필요한가?' 물었을 때 3분 안에 근거→결정→요구사항을 따라갈 수 있어야 한다"는 문구 강조.

**핵심 내용 요약:**
- KB는 "자료 보관함"이 아니라 팀원과 AI가 **같은 근거를 같은 구조로 탐색하는 작업 경로**로 설계
- `02-research-evidence.md`가 모든 주장에 근거 등급(🔵 확인됨·🟡 팀 합의·🔴 미검증)을 매김 — 예: Net Benefit 임계값(5만원·15%)은 🟡 실측 아닌 합의 상수라고 스스로 밝힘
- `06-open-questions.md`가 "근거 없어 아직 답하지 않는 질문"을 별도 관리

**발표 대본:**
> 리서치에서 가장 신경 쓴 건 "이 숫자가 진짜인가, 우리가 정한 값인가"를 항상 구분하는 것이었습니다. 예를 들어 저희 핵심 게이팅 기준인 "순혜택 5만원 이상, 그리고 15% 이상"이라는 임계값, 이거 사용자 조사로 나온 숫자가 아닙니다. 팀이 32시간 프로토타입을 위해 합의한 상수입니다. 그래서 저희는 이 값에 항상 노란 배지를 붙이고, Decision Log에 "왜 이 값인가, 언제 재검토하는가"까지 적어 뒀습니다. 근거 없이 아직 답 못 하는 질문들도 숨기지 않고 Open Questions 문서에 따로 모아뒀고요. 이게 저희가 생각하는 "고도화된 리서치"입니다 — 화려한 게 아니라, **뭘 모르는지도 아는 것**입니다.

## 슬라이드 5 — PRD: 목표와 성공 지표

**배점 매칭:** PRD → SRS 확장과 요구사항 추적성 — **20점** (도입부)

**화면 구성 제안:** 깔때기형 지표 트리. 최상단 "북극성 후보: 결론 수용률(결과 도달자 중 확정 비율)" → 산하 "Concierge Test 목표 ≥40%, 20% 미만이면 A-01 가정 재검토". 오른쪽에 G1~G6 목표 리스트 요약.

**핵심 내용 요약:**
- 북극성은 아직 "목표 미설정" 상태임을 숨기지 않고 명시 — 실사용자 데이터 확보 후 기준선 수립 예정
- 대신 Concierge Test(모집 40명, 유효 30명) 기준 **선택률 ≥40%**를 임시 성공 기준으로 둠, 20% 미만이면 핵심 가정 피벗
- "유지" 결론은 실패가 아니라 정상 결과이므로, 북극성 분모에서 원인(임계미달 vs 제약과다)을 구분해 측정 오염을 막음(D-009)

**발표 대본:**
> PRD에서 가장 정직하게 쓴 부분이 지표 섹션입니다. 저희는 "선택률 40%가 목표입니다"라고 자신 있게 말하지 않았습니다. 대신 "북극성 지표는 아직 목표를 못 정했다, 실사용자 데이터가 쌓여야 정할 수 있다"고 명시했고, 대신 Concierge Test — 그러니까 사람이 직접 계산을 도와주는 방식의 예비 테스트 — 에서 유효 30명 기준 선택률 40% 이상이면 계속 가고, 20% 미만이면 핵심 가정 자체를 다시 봐야 한다는 피벗 기준만 뒀습니다. 그리고 한 가지 더, "지금 카드 유지"라는 결과가 나왔을 때 이걸 실패로 셀지 성공으로 셀지도 고민했는데요, 진짜 임계 미달인지 사용자가 조건을 너무 좁게 잡아서인지 원인을 나눠서 기록하기로 했습니다. 지표 하나도 대충 정하지 않았다는 걸 보여드리고 싶었습니다.

## 슬라이드 6 — SRS 추적성: FR/UI/NFR/AC → GitHub Issue (★ 핵심 슬라이드)

**배점 매칭:** PRD → SRS 확장과 요구사항 추적성 — **20점** (핵심)

**화면 구성 제안:** `docs/TRACEABILITY.md` 표를 그대로 캡처하거나 재구성 — 열 구성: KB 근거 → PRD 목표 → SRS Requirement → Spec → GitHub Issue → 구현 → 검증. 한 행을 레이저 포인터로 짚듯 강조(예: FR-003 행). 우측에 "Must 요구사항에 열린 구현 경로가 없으면 완료로 보지 않는다"는 완료 기준 문구.

**핵심 내용 요약:**
- FR-001~FR-008(기능) · UI-001~UI-008(화면) · NFR-001~NFR-005(비기능) · AC-001~AC-013(수용기준) 전체가 표 하나로 연결됨
- 각 요구사항은 반드시 GitHub Issue #1~#9 중 하나 이상에 연결 — 연결 안 되면 "완료"로 안 침
- 예시 한 줄: **FR-003(Net Benefit 게이팅, ★핵심) → Issue #4·#7 → AC-004·AC-006·AC-013**
- FR-009(기준 대조 화면)는 **철회 이력을 지우지 않고 표에 "철회"로 남김** — 왜 뺐는지도 추적 가능하게

**발표 대본:**
> 이 표가 오늘 발표에서 가장 보여드리고 싶은 슬라이드입니다. 왼쪽부터 순서대로, KB에서 나온 근거가 → PRD의 어떤 목표에 연결되고 → SRS의 어떤 기능·화면·비기능 요구사항이 되고 → 어떤 기술 명세를 거쳐 → 몇 번 GitHub Issue로 실제 작업이 됐는지, 한 줄로 끝까지 따라갈 수 있습니다. 예를 들어 저희 핵심 기능인 FR-003 Net Benefit 게이팅은 Issue 4번과 7번으로 구현됐고, Acceptance Criteria 4번·6번·13번으로 검증됩니다. 그리고 저희는 한번 정했다가 뺀 요구사항도 지우지 않았습니다. FR-009라는 "과거·미래 기준 대조 화면"은 한때 있었지만 철회했는데, 이 표에 "철회"라고 그대로 남겨서 왜 뺐는지 나중에도 추적할 수 있게 했습니다. 요구사항 관리에서 중요한 건 다 만드는 게 아니라, **뺀 것도 왜 뺐는지 설명할 수 있는 것**이라고 생각합니다.

## 슬라이드 7 — 기술 근거: 규칙 엔진(Rule Engine)이 곧 제품

**배점 매칭:** PRD → SRS 확장과 요구사항 추적성 — **20점** (기술 구현 근거) / SDD·기술학습과도 연결

**화면 구성 제안:** 계산 흐름도. `FutureSpendPlan + HeldCard + BenefitRule → [규칙 엔진] → Net Benefit ≥ 50,000원 AND ≥ Gross×15%? → (Yes) 신규·유지·정리 조합 / (No) 현재 조합 유지`. 코드 스니펫으로 `src/domain/calc.ts`의 임계 판정 함수 일부 캡처.

**핵심 내용 요약:**
- 공식: `Net Benefit = Gross Benefit − (연회비 + 실적 재적립 손실 + 발급 대기 비용)`
- 이중 임계: `≥ 50,000원 AND ≥ Gross Benefit × 15%` — 절대값 하나만 쓰면 큰 혜택엔 사소한 개선에도 변경 권유, 상대값 하나만 쓰면 소액에도 신규 발급 남발 → 두 오류를 동시에 막음
- **금액과 설명 모두 AI가 만들지 않는다** — 결정론적 규칙 엔진 + 고정 템플릿, 같은 입력이면 항상 같은 결과(NFR-001)
- 실제 화면 예시(change_case): 가전·가구 840만원·여행 320만원·예식 480만원 입력 → **연 186,000원 더 유리** (+224,000 / −38,000), A카드 유지·B카드 정리·C카드 신규

**발표 대본:**
