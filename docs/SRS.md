## 3. 기능 요구사항 (FR)

### FR-001 미래지출 입력

| 필드 | 내용 |
| --- | --- |
| **Requirement** | 시스템은 사용자가 카테고리·금액·시점으로 미래 지출을 입력할 수 있게 해야 한다. 카테고리는 자유 입력을 허용하고, 지출 **증가·감소 양방향**을 처리해야 한다 |
| **Rationale** | 직접 확인한 경쟁 5곳 중 이 단계를 가진 곳 0곳(E-04 🔵). ⓐ 시간축의 유일한 진입점 |
| **Input** | 카테고리(자유 입력), 금액(원), 시점(월 — 기준일 +1~12개월) |
| **Rule** | 이벤트 필수 선택 단계를 두지 않는다. **감소 방향은 항목별 `+ 늘어요` / `− 줄어요` 토글로 받고 금액은 항상 양수로 입력받는다** (`T20`) — 마이너스 금액을 직접 입력받지 않는다. 방향은 `FutureSpendPlan.direction`에 저장한다 |
| **Output** | `FutureSpendPlan` 레코드 n건 |
| **AC** | AC-001 · AC-007 |
| **Source** | 2차 F-01 · KB `E-04` · `A-01` |
| **Priority** | Must |

### FR-002 미래지출 기준 혜택 계산

| 필드 | 내용 |
| --- | --- |
| **Requirement** | 시스템은 사용자가 확인한 앞으로 12개월 지출 계획을 기준으로 현재 조합과 후보 조합의 예상 혜택을 계산해야 한다 |
| **Rationale** | G2 — 과거 소비만 보는 비교를 넘어 사용자가 확인한 미래 계획을 계산 기준으로 삼는다 |
| **Input** | `FutureSpendPlan`, `HeldCard`, `BenefitRule` (Mock) |
| **Rule** | **계산 기간 = 기준일로부터 12개월** (`T15`). 사용자가 시점을 입력한 달은 그 값을 쓰고, **입력이 없는 달은 과거 패턴(`PastSpend`)을 기저로 채운다.** 모든 결과 금액은 **12개월 합계**이며 화면에는 *"연 n원"*으로 표기한다. 연회비는 연 단위 그대로 차감하며 안분하지 않는다.<br>입력 화면의 값은 과거 소비 패턴으로 미리 채운 **제안 초안**이다. 사용자가 항목을 추가·수정하지 않았더라도 **`이 계획대로 계산하기`를 누르면 화면에 보이는 전체 값을 앞으로 12개월의 지출 계획으로 확인한 것**으로 본다(`T37`). 결과에는 *"사용자가 확인한 앞으로 12개월의 지출 계획을 반영했습니다"*라고 밝힌다. 별도의 최소 입력 건수·금액 비율은 두지 않는다. 모든 항목을 삭제했거나 금액이 전부 0이면 결과를 반환하지 않는다(`AC-001`). 확인된 계획을 임의로 증감하지 않고 그대로 한 번 계산한다 |
| **Output** | `Calculation` 1건 |
| **AC** | AC-001 · AC-010 |
| **Source** | 2차 F-03 · G2 · `T37` |
| **Priority** | Must |

### FR-003 조합 최적화 · Net Benefit 게이팅 ★ 핵심

| 필드 | 내용 |
| --- | --- |
| **Requirement** | 시스템은 카드별 상태를 **신규·유지·정리** 중 하나로 표시한 조합 후보를 생성하고, 각 후보의 **Net Benefit이 임계값을 넘을 때만** 변경을 제안해야 한다. **임계 미달이면 모든 보유 카드를 유지하는 현재 조합을 반환**한다.<br>**조합 크기는 사용 카드 최대 2장, 신규는 최대 1장이다** (`T6`).<br>유지 결과의 원인은 `임계미달` 또는 `제약과다`로 `Calculation.hold_reason`에 기록한다 (`T38`) |
| **Rationale** | G3 — 바꿀 가치가 있을 때만 권한다. 경쟁자 체인에 없는 단계이며, "유지"를 정답으로 반환하는 유일한 설계. 출처는 핀트의 Net Benefit 게이팅(2차 방법론 11번) |
| **Input** | `Calculation`, `HeldCard`, `Constraint` |
| **Rule** | `Net Benefit = Gross Benefit − (연회비 + 실적 재적립 손실 + 발급 대기 비용)` — **전환비용 3항목** 확정.<br>**연회비는 안분하지 않는다**(`T15`). 발급 시점이 12개월 창의 **7개월 이후**면 근거 화면에 *"이 카드의 연회비는 12개월 창에 통째로 반영됐습니다"*를 고지한다 (`T40`).<br>**임계값 = `Net Benefit ≥ 50,000원` AND `Net Benefit ≥ Gross Benefit × 15%`** — 이중 조건, 연 단위 (`D-002` · `T16`).<br>둘 중 하나라도 미달 → 모든 보유 카드를 **유지**. 둘 다 충족 → 카드별로 **신규·유지·정리** 상태를 부여한다.<br>유지 반환 시 제약을 완화한 후보가 임계를 넘으면 `제약과다`, 그렇지 않으면 `임계미달`로 기록한다. `제약과다`일 때만 *"제약을 풀면 더 나은 조합이 있어요"*를 노출한다 (`T38`).<br>결론 조합의 사용 카드는 최대 2장이고 신규는 최대 1장이다. `정리`는 해지 대행이 아니라 조합에서 제외한다는 표시이며 실행 버튼을 두지 않는다. 결과에는 **"사용 카드 2장·신규 1장 이내에서의 최선"**이라고 범위를 밝힌다 (`T39`) |
| **Output** | `PlanCandidate` (조합 구성 · Gross Benefit · 전환비용 3항목 · Net Benefit · **임계 통과 여부**) |
| **AC** | **AC-004** · AC-006 · **AC-013**(`T38`) |
| **Source** | 2차 F-04 · 정본 6-1절 · **D-002** |
| **Priority** | **Must — 이 계산이 제품의 전부** |

> **✅ D-002 확정 (2026-08-31 · `T16`)** — `Net Benefit ≥ 50,000원` **AND** `≥ Gross × 15%`.
> 실측이 아니라 **프로토타입 계산을 위한 팀 합의 상수 🟡**입니다. 사용자 행동 지표와 같은 근거로 취급하지 않습니다.
>
> **왜 이중 조건인가** — 절대값만 쓰면 Gross 90만원에서 6.7% 개선에 변경을 권하게 되고, 상대값만 쓰면
> 연 3천원 차이로 신규 발급을 권하는 과잉 제안을 만들 수 있습니다. 근거 화면에서
> *"연 5만원 미만이거나 전체 혜택의 15%에 못 미치면 바꿀 가치가 없다고 봅니다"*로 한 줄 설명이 됩니다.
>
> **확정에 이른 판단 이력**
> 공식 모양과 전환비용 3항목은 2차 정본에서 확정됐습니다. 비어 있는 것은 **임계값 상수 하나**입니다.
> 2차는 D2를 "착수 전 선결 🔴"로 남겼고 *"추정 임계값으로 0%를 판정하는 건 의미가 없다"*고 했습니다 —
> **사업 착수 기준으로는 맞지만 프로토타입에는 적용되지 않습니다.** 이 프로토타입이 검증하는 것은
> 계산의 정확성이 아니라 **조합안을 이해하는 UX**이기 때문입니다.
> → 절대·상대 임계를 **팀 합의 상수 🟡**로 고정하고 `D-002`에 성격과 함께 기록했습니다.

### FR-004 결제수단 배분

| 필드 | 내용 |

| **Requirement** | 시스템은 확정된 조합에 대해 카드별 역할과 배분 금액을 산출해 제시해야 한다 |

### 6-2. 인터페이스

프로토타입은 별도 백엔드 서버를 만들지 않지만, Next.js Server Actions와 Prisma를 사용하는 최소 서버 계층을 둔다. 외부 공개 REST API는 만들지 않고, 구현에 필요한 입력·출력 계약을 먼저 고정한다.

| 인터페이스 | 입력 | 출력·제약 |
| --- | --- | --- |
| `calculatePlan()` | 확인된 `FutureSpendPlan`, `PastSpend`, `HeldCard`, `BenefitRule`, `Constraint` | `Calculation` 1건과 단일 `PlanCandidate`; 미래 입력 0건·미확정 계획·필수 근거 누락이면 결과를 반환하지 않는다 |

### 11.1 화면에서 확인할 수 있는 상태

독자가 구현 배경지식 없이도 정책을 확인할 수 있도록 정상 흐름은 [`BUSINESS_SEQUENCE.md`](diagrams/BUSINESS_SEQUENCE.md), 예외 흐름은 [`TECHNICAL_DESIGN.md`](diagrams/TECHNICAL_DESIGN.md)의 6장을 참조한다.

- 정상 상태: 근거 6개가 모두 확인되면 추천 결과와 적용 CTA를 표시한다.
- 차단 상태: 근거 하나라도 누락되면 추천 결과와 적용 CTA를 숨기고 누락 항목·사유를 표시한다.
- 복구 상태: 누락 근거를 보완한 뒤 동일 입력으로 재검증하고, 검증 완료 시 정상 결과로 전환한다.

SRS Light에서는 위 다이어그램을 본문에 복사하지 않고 참조 링크로 유지한다. 정상 흐름은 [`BUSINESS_SEQUENCE.md`](diagrams/BUSINESS_SEQUENCE.md), 예외·오류·복구 흐름은 [`TECHNICAL_DESIGN.md`](diagrams/TECHNICAL_DESIGN.md)의 6장, 데이터 구조는 같은 문서의 3~5장을 기준으로 한다. 이 링크들은 SRS의 요구사항·우선순위·수용 기준을 대체하지 않는다.
