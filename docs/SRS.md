```

  → [0-B] 현재 혜택 요약   사용자 지정 iPhone 17 화면 기준
```

## 3. 기능 요구사항 (FR)

### FR-001 미래지출 입력

| 필드 | 내용 |
| --- | --- |
| **Requirement** | 시스템은 사용자가 카테고리·금액·시점으로 미래 지출을 입력할 수 있게 해야 한다. 카테고리는 자유 입력을 허용하고, 지출 **증가·감소 양방향**을 처리해야 한다 |
| **Rationale** | 직접 확인한 경쟁 5곳 중 이 단계를 가진 곳 0곳(E-04 🔵). ⓐ 시간축의 유일한 진입점 |
| **Input** | 카테고리(자유 입력), 금액(원), 시점(월 — 기준일 +1~12개월) |
| **Rule** | 이벤트 필수 선택 단계를 두지 않는다. **감소 방향은 항목별 `+ 늘어요` / `− 줄어요` 토글로 받고 금액은 항상 양수로 입력받는다** (`T20`) — 마이너스 금액을 직접 입력받지 않는다. 방향은 `FutureSpendPlan.direction`에 저장한다 |
| **Output** | `FutureSpendPlan` 레코드 n건 |
| **AC** | AC-001 · AC-007 |
| **Source** | 2차 F-01 · KB `E-04` · `A-01` |
| **Priority** | Must |

### FR-002 시나리오 계산 (3개)

| 필드 | 내용 |
| --- | --- |
| **Requirement** | 시스템은 입력된 미래 지출에 대해 **적게·예상대로·많이 3개 시나리오를 모두 사전 계산**하고, 탭 전환 시 재계산 없이 제공해야 한다 |
| **Rationale** | G6 — 예측이 틀려도 답을 준다. 뱅크샐러드는 후보 카드 1장과만 비교(E-05 🔵) |
| **Input** | `FutureSpendPlan`, `HeldCard`, `BenefitRule` (Mock) |
| **Rule** | **계산 기간 = 기준일로부터 12개월** (`T15`). 사용자가 시점을 입력한 달은 그 값을 쓰고, **입력이 없는 달은 과거 패턴(`PastSpend`)을 기저로 채운다.** 모든 결과 금액은 **12개월 합계**이며 화면에는 *"연 n원"*으로 표기한다. 연회비는 연 단위 그대로 차감하며 안분하지 않는다.<br>입력 화면의 값은 과거 소비 패턴으로 미리 채운 **제안 초안**이다. 사용자가 항목을 추가·수정하지 않았더라도 **`이 계획대로 계산하기`를 누르면 화면에 보이는 전체 값을 앞으로 12개월의 지출 계획으로 확인한 것**으로 본다(`T37`). 결과에는 *"사용자가 확인한 앞으로 12개월의 지출 계획을 반영했습니다"*라고 밝힌다. 별도의 최소 입력 건수·금액 비율은 두지 않는다. 모든 항목을 삭제했거나 금액이 전부 0이면 확인할 계획이 없으므로 결과를 반환하지 않는다(`AC-001`).<br>**적게 = 입력값 −20% · 예상대로 = 입력값 그대로 · 많이 = 입력값 +20%.** ±20%는 **사용자가 확인한 미래지출 계획에만** 적용하고 과거 패턴 기저에는 적용하지 않는다. 세 탭 모두 동일한 계산 로직을 각 지출 가정에 독립 적용한다. **"예상대로"가 기본 탭이다** (`T36` 확정) — 화면이 열리면 이 결론이 보인다. **기본 탭은 프로필에 따라 바뀌지 않는 고정값이다** — 결론이 보수적인 탭을 자동 선택하지 않는다. 각 탭에 지출 가정을 캡션으로 명시한다(예: *"예상보다 20% 적게 쓸 경우"*) |
| **Output** | `Calculation` 3건 (scenario 필드로 구분) |
| **AC** | AC-005 |
| **Source** | 2차 F-03 · 정본 3-1절 · **D-003** |
| **Priority** | Must |

> **±20%의 성격 — 팀 합의 상수 🟡.** 2차는 D5(시나리오 증감 폭)를 🔴 미정으로 남겼지만,
> 정본 3-1절의 캡션 예시가 이미 *"예상보다 20% 적게 쓸 경우"*로 20%를 쓰고 있습니다.
> 실측이 아니라 **문서에 있는 값을 프로토타입 계산 상수로 고정**한 것입니다. 사용자 행동 지표와 같은 근거로 취급하지 않습니다. → `D-003`

> **기본 탭이 왜 "예상대로"인가 — `T36`.** 기본값이 곧 사용자가 처음 보는 결론이라 `GR2`
> (*불필요 신규카드 추천 0%*)에 직결됩니다. 그럼에도 보수적인 *적게*를 기본으로 두지 않는 이유는,
> **사용자가 방금 입력한 값이 기본이 아니면 입력 노동이 배신당하기 때문**입니다 — 가정 `A1`
> (*"미래 입력의 수고가 혜택 보상으로 정당화된다"*)이 이 서비스 전체의 전제이고, 기본 탭이 입력값과
> 다르면 그 전제를 화면이 먼저 깹니다. `T20`에서 입력을 증감 양방향으로 받기로 했으므로
> *"예상대로"*는 이미 **사용자의 판단이 반영된 값**입니다.
>
> **과잉 추천 방어는 기본 탭이 아니라 `D-002` 이중 게이팅이 담당합니다.** 기본 탭을 보수적으로 두는 것은
> 게이팅을 두 번 거는 것이고, 그러면 변경 제안이 나오는 케이스를 만들기 어려워져 `T15`에서 3개월 horizon을
> 버린 것과 같은 문제가 생깁니다.
>
> **프로필 2개가 기본 탭 하나로 `AC-004` 양쪽을 다 보여줍니다** — 이서연은 *변경*(`Net 186,000`),
> 강민재는 *유지*(`Net 31,000`). 기본 탭을 바꿀 필요 없이 게이팅 분기가 시연됩니다.

### FR-003 조합 최적화 · Net Benefit 게이팅 ★ 핵심

| 필드 | 내용 |
| --- | --- |
| **Requirement** | 시스템은 보유 카드의 유지·해지·신규추가 조합 후보를 생성하고, 각 후보의 **Net Benefit이 임계값을 넘을 때만** 변경을 제안해야 한다. **임계 미달이면 "현재 조합 유지"를 결론으로 반환**한다.<br>**조합 크기는 사용 카드 최대 2장, 신규는 최대 1장이다** (`T6`) |
| **Rationale** | G3 — 바꿀 가치가 있을 때만 권한다. 경쟁자 체인에 없는 단계이며, "유지"를 정답으로 반환하는 유일한 설계. 출처는 핀트의 Net Benefit 게이팅(2차 방법론 11번) |
| **Input** | `Calculation`(시나리오별), `HeldCard`, `Constraint` |
| **Rule** | `Net Benefit = Gross Benefit − (연회비 + 실적 재적립 손실 + 발급 대기 비용)` — **전환비용 3항목** 확정.<br>**연회비는 안분하지 않는다**(`T15`). 발급 시점이 12개월 창의 **7개월 이후**면 근거 화면에 *"이 카드의 연회비는 12개월 창에 통째로 반영됐습니다"*를 고지한다 — **규칙을 바꾸지 않고 고지로 처리하며, 이 왜곡은 계산 오류율 판정 대상이 아니다**(`T40`).<br>**임계값 = `Net Benefit ≥ 50,000원` AND `Net Benefit ≥ Gross Benefit × 15%`** — 이중 조건, 연 단위 (`D-002` · `T16`).<br>둘 중 하나라도 미달 → **"현재 조합 유지"** 반환.<br>둘 다 충족 → 조합 변경안 반환.<br>**조합 후보 생성 범위 (`T6`)** — 카드별 상태는 `유지 / 해지 / (신규) 추가` 3종. **결론 조합의 사용 카드는 최대 2장**이고 **신규 발급은 최대 1장**이다. 해지는 후보에 남긴다 — `FR-008`·`AC-003`의 트리거이자 "카드를 줄이는 것"도 정답의 하나이기 때문이다 |
| **Output** | `PlanCandidate` (조합 구성 · Gross Benefit · 전환비용 3항목 · Net Benefit · **임계 통과 여부**) |
| **AC** | **AC-004** · AC-006 |
| **Source** | 2차 F-04 · 정본 6-1절 · **D-002** |
| **Priority** | **Must — 이 계산이 제품의 전부** |

> **✅ D-002 확정 (2026-08-31 · `T16`)** — `Net Benefit ≥ 50,000원` **AND** `≥ Gross × 15%`.
> 실측이 아니라 **프로토타입 계산을 위한 팀 합의 상수 🟡**입니다. 사용자 행동 지표와 같은 근거로 취급하지 않습니다.
>
> **왜 이중 조건인가** — 절대값만 쓰면 Gross 90만원에서 6.7% 개선에 변경을 권하게 되고, 상대값만 쓰면
> 연 3천원 차이로 신규 발급을 권해 `G-01`(불필요한 신규카드 방지)과 충돌합니다. 근거 화면에서
> *"연 5만원 미만이거나 전체 혜택의 15%에 못 미치면 바꿀 가치가 없다고 봅니다"*로 한 줄 설명이 됩니다.
>
> **확정에 이른 판단 이력**
> 공식 모양과 전환비용 3항목은 2차 정본에서 확정됐습니다. 비어 있는 것은 **임계값 상수 하나**입니다.
> 2차는 D2를 "착수 전 선결 🔴"로 남겼고 *"추정 임계값으로 0%를 판정하는 건 의미가 없다"*고 했습니다 —
> **사업 착수 기준으로는 맞지만 프로토타입에는 적용되지 않습니다.** 이 프로토타입이 검증하는 것은
> 계산의 정확성이 아니라 **조합안을 이해하는 UX**이기 때문입니다.

## 7. 상태 전이와 중요한 예외

2차 상태 전이 4종 중 **3종이 구현 대상**입니다. 마이데이터 동의 전이는 D-001로 인해 해당 없습니다.

| 객체 | 상태값 | 전이 규칙 | 구현 |
| --- | --- | --- | --- |
| ~~마이데이터 동의~~ | 미동의 → 동의 → (만료/철회) | — | **해당 없음** (D-001 Mock) |

| **PlanCandidate** | 제시 → (선택 / 미선택) → **만료** | `rule_version` 변경 또는 기준일 +30일 경과 시 만료. 만료 조합안은 재계산 없이 실행 대상이 되지 않는다 | Could — 만료 조건만 표기 |

| 상태 | 진입 조건 | 화면 |
| --- | --- | --- |
| Loading | 계산 실행 중 | 3개 시나리오 사전 계산 진행 표시 |

## 8. Acceptance Criteria와 검증 방법

2차 AC 8건 중 **7건**이 프로토타입에서 판정 가능하고, `T25`에서 **AC-008**, `T35`에서 **AC-009**, `T37`에서 **AC-010**을 신설해 총 **10건**입니다.
신설 사유는 아래 표 `AC-008` 행과 FR-008을 참고하세요 — 북극성이 걸린 확정 액션을 판정할 AC가 없었습니다.

| ID | Given | When | Then | 대응 FR |
