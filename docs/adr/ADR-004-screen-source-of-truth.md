# ADR-004 — 화면의 정본은 기준본 HTML이고, 데이터의 정본은 DB다

- 상태: Accepted
- 결정일: 2026-09-03
- 함께 읽는다: `ADR-001`(Mock First) · `ADR-002`(결정론적 엔진) · `ADR-003`(세션 상태)

## 맥락

`docs/prototype/cardfit-prd-srs-v0.4.html`(이하 기준본)은 화면·문구·인터랙션을 한 파일에 담은
검증용 프로토타입이고, PRD·SRS가 이미 이 흐름으로 동기화되어 있다. 구현이 기준본보다
뒤처지면 화면 계약이 두 벌로 갈라진다.

여기서 갈림길이 하나 있다. 기준본은 시나리오별 카드 조합과 혜택 금액을 **표로 고정한 Mock**이라,
규칙 엔진이 DB Seed로 계산한 값과 숫자가 어긋난다. 이때 화면을 기준본 숫자에 맞출 것인가,
엔진 계산값에 맞출 것인가.

`app/prototype-v0.4-port` 브랜치는 전자를 택해, 화면 데이터의 정본을 `src/fixtures/prototype.ts`로
옮기고 `/app/*`를 정적 프리렌더로 바꿔 요청 경로에서 DB를 뺐다. 발표 중 DB 장애가 데모를
멈추지 못한다는 장점이 있지만, 화면 데이터와 DB Seed가 두 벌로 갈라진다.

## 결정

**화면 구조·문구·인터랙션이 기준본과 다르면 기준본이 옳다. 그러나 화면에 뜨는 금액의 정본은
DB Seed를 읽어 규칙 엔진이 계산한 값이다.**

1. **레이아웃·문구·인터랙션은 기준본을 따른다.** 구현이 기준본보다 앞서 나가지 않는다.
   기준본에 없는 화면과 컨트롤을 만들지 않는다.
2. **금액은 `src/domain`의 규칙 엔진이 계산한다.** 기준본 JS의 고정 표를 코드로 옮기지 않는다.
   기준본의 숫자는 레이아웃을 잡기 위한 자리값이지 계산 결과가 아니다.
3. **요청 경로에서 DB를 읽는다.** `/app` 레이아웃이 `loadProfile()`로 Fixture를 조립해
   내려준다. Seed를 바꾸면 화면이 따라 바뀌어야 하고, 그래야 실연동 전환 지점(`ADR-001`)이
   런타임에서 실제로 검증된다.
4. **화면 데이터를 담은 별도 Fixture 파일을 만들지 않는다.** `src/fixtures/**`는 테스트 정답셋과
   카드 이미지·카테고리 목록처럼 계산에 관여하지 않는 자산만 담는다.

## 채택하지 않은 대안

`app/prototype-v0.4-port`의 정적 프리렌더 안을 채택하지 않는다. 발표 안정성은 얻지만
**Prisma·Supabase·Repository 계층이 요청 경로에서 빠지면서 검증 대상에서 사라진다.**
프로토타입의 목적이 실연동 전환 가능성을 확인하는 것이라, 그 계층이 죽으면 남는 게 화면뿐이다.
DB 장애 대비는 `/app` 레이아웃의 오류 화면과 복구 안내로 처리한다.

## 결과

- 좋음 — 화면 구조가 기준본과 1:1로 대응하면서 금액은 엔진이 만든 값 하나로 유지된다.
- 좋음 — Seed·규칙을 고치면 화면이 따라 바뀐다. 실연동 전환 지점이 계속 살아 있다.
- 나쁨 — 화면의 숫자가 기준본 HTML의 숫자와 다르다. 기준본을 볼 때 금액이 아니라
  레이아웃을 대조해야 한다.
- 나쁨 — 배포와 데모가 DB 가용성에 묶인다.

## 되돌리는 조건

발표 당일 DB 가용성을 확보할 수 없다고 판단되면, 요청 경로만 정적 스냅샷으로 바꾸고
Repository 계층은 그대로 둔다. 데이터 정본을 화면 쪽으로 옮기지는 않는다.
