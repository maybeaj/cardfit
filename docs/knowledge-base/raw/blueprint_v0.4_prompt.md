# CardFit Mobile UX Blueprint — HTML Prototype 제작 프롬프트

너는 금융서비스와 핀테크 도메인에 익숙한 시니어 Product Designer이자 Product Manager다.

아래 GitHub 저장소의 확정 자료를 기반으로, **CardFit이라는 미래지출 기반 카드조합 추천 서비스의 모바일 UX Blueprint를 단일 HTML 문서로 제작하라.**

단순 와이어프레임이나 화면 목록이 아니라, 실제 iPhone 앱이 구동되는 것처럼 보이는 **고해상도 사용자 프로토타입 + 화면별 UX/PM Blueprint 설명**이 함께 존재해야 한다.

# 0. 가장 중요한 원칙

CardFit은 **카드 1장을 추천하는 서비스가 아니다.**

CardFit의 핵심은 사용자의:

- 현재 보유카드
- 과거 소비 데이터
- 앞으로 발생할 미래 소비 변화
- 카드별 전월실적
- 혜택구간
- 혜택한도
- 연회비
- 사용자가 허용한 최대 카드 수

를 함께 계산해서,

> **현재 보유카드 중 무엇을 유지하고,
> 무엇의 역할을 줄이거나 정리하고,
> 필요한 경우 어떤 신규카드를 추가할지**

를 **하나의 카드 조합으로 최적화하는 서비스**다.

따라서 결과의 추천 단위는 항상:

> **Card Combination / Payment Portfolio**

여야 한다.

절대로 결과를
`추천 카드 1장`
중심의 서비스처럼 설계하지 마라.

# 4. CardFit의 서비스 정의

CardFit은 소비가 곧 바뀔 사람을 위해 카드 조합을 다시 계산해주는 서비스다.

마이데이터를 통해:

- 과거 소비기록
- 현재 보유카드

를 자동으로 확보한다.

사용자는 추가로:

- 앞으로 어디에
- 얼마를
- 언제쯤 사용할지

정도만 입력한다.

CardFit은 이를 기반으로 보유카드와 신규카드 후보의:

- 전월실적
- 실적구간
- 혜택한도
- 연회비
- 카드 간 소비 이동에 따른 손실

등을 계산해서 가장 유리한 **카드 조합 + 결제 운용방식**을 제안한다.

복잡한 카드 혜택 계산은 시스템이 수행하고,
사용자는 계산 결과와 근거를 이해하고 최종 결정을 내린다.

# 5. 핵심 사용자

대표 Core Persona는:

- 결혼을 앞둔 30대
- 1~3개월 안에 평소와 다른 고액지출 발생
- 가전·가구·여행·백화점·각종 일반결제 증가
- 이미 신용카드를 사용하고 있음
- 마이데이터 사용자

이다.

그러나 서비스 UX에서 사용자가 반드시:

- 결혼
- 이사
- 출산
- 입주

등의 이벤트를 선택하게 만들지 마라.

CardFit의 계산 단위는 **Life Event가 아니라 Spending Change**다.

# 6. 미래지출 입력 UX — 매우 중요

사용자는 미래를 정확하게 예측할 수 없다.

따라서 미래지출 입력 단계의 목표는:

> 정교한 금융입력 화면

이 아니라

> **사용자가 알고 있는 정도의 미래 소비만 부담 없이 입력**

하게 만드는 것이다.

기본 입력값은 다음 3개만 사용한다.

### 필수 입력

1. 소비 카테고리
2. 예상 금액
3. 예상 시점

예:

- 가전·전자 / 840만원 / 3개월 내
- 여행·항공 / 320만원 / 1개월 내
- 백화점 / 500만원 / 3개월 내

---

# 7. 입력 단계에서 받지 말아야 하는 정보

다음 정보는 사용자가 미래 소비를 입력하는 단계에서 요구하지 마라.

- 할부 여부
- 할부 개월 수
- 무이자할부 기간
- 신규카드 예상 발급일
- 카드 발급 완료일

사용자가 아직 어떤 카드로 결제할지도 결정하지 않은 상태에서
이런 정보를 요구하면 불확실성을 추가하고 입력 이탈 가능성을 높인다.

필요한 카드 Rule은 시스템이 계산 과정에서 처리한다.

---

# 8. 소비 카테고리 설계 — 매우 중요

미래지출 카테고리는:

- 결혼
- 이사
- 입주
- 예식

같은 **Life Event 카테고리로 만들지 마라.**

이런 카테고리는 카드 혜택 Rule에 직접 연결되지 않기 때문이다.

예를 들어:

`이사·입주 1,000만원`

이라는 정보만으로는 어떤 카드가 유리한지 계산할 수 없다.

실제 소비는:

- 가전
- 가구
- 백화점
- 온라인 쇼핑
- 여행
- 일반결제

등으로 분해되어야 한다.

따라서 카테고리는 **카드 혜택 Rule과 연결 가능한 소비유형**으로 설계한다.

예시:

- 온라인 쇼핑
- 백화점·아울렛
- 대형마트
- 가전·전자제품
- 가구
- 여행·항공
- 해외결제
- 외식·카페
- 교통
- 통신
- 구독
- 주유
- 의료
- 교육
- 일반결제

반드시:

> **일반결제 / 기타**

카테고리를 제공한다.

카드 혜택과 명확히 연결되지 않는:

- 웨딩홀
- 이사업체
- 기타 고액결제

등은 억지로 다른 카테고리에 매핑하지 않는다.

# 9. MyData 전제

MVP부터 MyData가 연결되어 있다고 전제한다.

따라서 사용자가 직접 입력할 필요가 없는 정보는 최대한 다시 묻지 않는다.

MyData에서 확보:

- 최근 소비
- 소비 카테고리
- 현재 보유카드

사용자가 입력:

- 미래에 달라질 소비

이 구조를 지켜라.

# 10. 첫 화면

첫 화면은 **추천 화면이 아니다.**

현재 상태를 보여주는 Diagnosis 화면이다.

예:

### 내 카드 사용 현황

A카드
- 주 사용 카드

B카드
- 혜택 활용 낮음

D카드
- 월 혜택한도 근접

이 단계에서:

- 유지
- 정리
- 신규

판정을 내리지 마라.

미래지출을 입력하기 전에 이미 추천한 것처럼 보이면
CardFit의 핵심 논리가 무너진다.

첫 화면 핵심 메시지:

> **앞으로 큰 지출이 있다면 지금 분석 결과가 달라질 수 있어요.**

Primary CTA:

> **앞으로 쓸 돈 반영하기**

# 11. 사용자 제약조건

필요한 최소 제약만 받는다.

예:

### 최대 몇 장까지 관리할까요?

`− 3장 +`

### 새 카드도 비교할까요?

`ON / OFF`

입력항목이 과도하게 늘어나지 않도록 한다.

복잡한 preference questionnaire는 만들지 마라.

# 12. Spending Scenario

미래 소비는 정확한 하나의 숫자라고 가정하지 않는다.

CardFit은 다음 3개 시나리오를 제공한다.

> 적게 | 예상대로 | 많이

### 기본 활성 탭

**예상대로**

사용자가 입력한 예상금액을 기준으로 결과 화면이 열린다.

`적게`와 `많이`는 sensitivity analysis용 보조 탐색이다.

# 13. 시나리오 표현법

시나리오 화면에서 지나치게 많은 정보를 한 번에 보여주지 마라.

금지 예:

> 월 평균 ₩3,499,000 지출 가정
> 총 ₩20,992,000 · 입력 예상 대비 +₩4,592,000 (+28%) · 6개월 계획

이런 설명은 모바일에서 지나치게 길다.

기본 화면에서는 사용자가 지금 필요한 정보만 보여준다.

예:

### 많이
**계획 지출 2,099만원**

그리고:

`시나리오 기준 보기 ›`

를 누르면 Bottom Sheet 또는 Accordion에서:

- 입력값 대비 증감액
- 증감률
- 계산 기간

등을 확인할 수 있게 한다.

Progressive Disclosure를 사용한다.

# 14. 결과 화면의 가장 중요한 정보 위계

결과 첫 화면은:

# Benefit First

구조여야 한다.

사용자가 가장 먼저 알고 싶은 질문:

> **그래서 내가 얼마나 더 받을 수 있는데?**

에 먼저 답한다.

따라서 첫 결과의 Hero는:

### 이 지출 계획이라면

# **예상 추가 혜택 +239,000원**

같은 형태가 되어야 한다.

미래 결과이므로:

- 확정 혜택
- 보장 혜택

처럼 표현하지 않는다.

반드시:

- 예상
- 이 지출 계획이라면
- 약

등 적절한 불확실성 표현을 사용한다.

# 16. 추천 단위 — CARD COMBINATION

결과 화면에 `추천 카드`라는 제목을 사용하지 마라.

반드시:

# 추천 카드 조합

으로 표현한다.

예:

### 추천 카드 조합

**A 유지 · B 정리 · C 신규**

각 카드의 역할을 짧게 표시한다.

`유지`

B카드
`정리 검토`

C카드
`신규`
여행·해외 및 남은 고액지출 담당

# 17. 카드 한 장을 Hero로 만들지 마라

C카드가 신규 추천되더라도:

> C카드 추천

을 결과의 핵심 메시지로 사용하지 않는다.

C카드는 **최종 카드조합을 구성하는 한 요소**다.

CardFit의 가치:

> 좋은 카드 하나를 찾는 것

이 아니라

> **현재 카드 포트폴리오를 미래 소비에 맞게 재배치하는 것**

이다.

---

# 18. Net Benefit Gate

CardFit은 신규카드를 무조건 추천하지 않는다.

현재 카드조합과 후보 카드조합의 실질적인 혜택 차이가 충분하지 않을 경우:

> **현재 카드 조합을 유지하세요**

도 정상적인 결과다.

따라서 Prototype에서는 최소한:

### 변경 추천 Branch
A 유지 + B 정리 + C 신규

와

### 유지 Branch
현재 카드 조합 유지

두 상태를 모두 표현한다.

---

# 19. 시나리오별 조합이 달라질 수 있어야 한다

`적게 / 예상대로 / 많이`는 숫자만 달라지는 탭이 아니다.

지출 규모에 따라 **추천 카드조합 자체가 바뀔 수 있어야 한다.**

예:

### 적게
현재 카드 조합 유지

### 예상대로
A 유지 + B 정리 + C 신규

### 많이
A + C 중심 조합 또는 카드별 배분 변화

따라서 프로토타입에서도 각 시나리오를 누르면:

- 예상 추가 혜택
- 유지/변경 Gate
- 추천 카드조합

이 실제로 달라져야 한다.

---

# 20. 결과 화면의 추천 카드 조합 표현

결과 첫 화면에서 카드조합은 너무 상세하게 설명하지 않는다.

예:

### 추천 카드 조합

**A 유지 · B 정리 · C 신규**

A카드 `유지`
B카드 `정리`
C카드 `신규`

정도만 먼저 보여준다.

상세한 이유는 별도 화면에서 확인한다.

---

# 21. 결과 화면 Shortcut

기본 User Flow는 유지한다.

하지만 사용자가 반드시 모든 화면을 순서대로 통과할 필요는 없다.

결과 화면에서 빠르게 이동할 수 있는 Shortcut을 제공한다.

예:

- `결제 순서`
- `계산 근거`
- `적용하기`

따라서 사용자는:

### 빠른 사용자
결과 → 적용

### 실행 방법이 궁금한 사용자
결과 → 결제 순서 → 적용

### 신뢰 검증이 필요한 사용자
결과 → 계산 근거 → 결제 순서 → 적용

처럼 이동할 수 있다.

다만 전체 Blueprint의 기본 논리 흐름은 유지한다.

# 22. Payment Sequence — 매우 중요

CardFit의 결제 설계는 단순히:

> 가전은 C카드
> 여행은 B카드
> 예식은 A카드

처럼 카테고리별로 카드를 나누는 방식이 아니다.

카드 혜택은 대부분:

- 전월실적
- 실적구간
- 월 혜택한도

가 있기 때문에,

CardFit은 **카드 사용 순서**를 설명해야 한다.

예:

### 이번 결제 순서

#### STEP 1
**A카드 50만원까지 먼저 사용**

전월실적 조건 충족

↓

#### STEP 2
**A카드 혜택한도까지 사용**

할인·적립 가능한 결제를 우선 사용

↓

#### STEP 3
**이후 결제는 C카드**

A카드 혜택한도를 소진한 뒤 보조카드 사용

---

# 23. Category Exception

모든 소비를 무조건 위 순서대로 사용하지는 않는다.

특정 카테고리 혜택이 강한 경우 예외처리를 한다.

예:

### ✈ 여행·해외 결제

**C카드를 우선 사용하세요**

해외 결제 수수료 또는 여행 관련 혜택이 더 유리하기 때문이다.

따라서 결제 로직은:

> **실적·혜택한도 기반 기본 Sequence
> + 특정 혜택 카테고리 Exception**

구조로 표현한다.

---

# 24. Calculation Evidence

사용자가 예상 추가혜택 숫자를 보면:

> 왜 이 금액이지?

라는 의문을 가질 수 있다.

이를 해결하기 위해:

# Benefit → Payment Sequence → Evidence

순서로 정보를 제공한다.

계산근거 화면에서는 먼저 혜택을 금액으로 분해한다.

예:

### 예상 추가 혜택

A카드 실적 충족 효과
`+96,000원`

A카드 혜택한도 활용
`+60,000원`

C카드 여행·해외 혜택
`+121,000원`

C카드 추가 연회비
`−38,000원`

---

### 예상 실질 추가 혜택

# +239,000원

그다음 사용자가 원할 경우 카드별 Rule을 펼쳐볼 수 있게 한다.

---

# 25. 사용자 화면에서는 내부 기술 용어를 최소화

사용자 화면에 다음 표현을 직접 노출하지 마라.

- Rule Engine
- Optimization Engine
- Net Benefit
- Deterministic Engine
- LLM

이 용어는 Blueprint의 SYSTEM / PM Annotation에만 사용한다.

사용자에게는:

- 예상 추가 혜택
- 바꾸면 더 받을 수 있는 금액
- 실적
- 혜택한도
- 연회비
- 계산 근거

처럼 이해 가능한 언어를 사용한다.

---

# 26. AI 역할

혜택 금액 계산은 AI가 임의로 계산하는 것처럼 표현하지 않는다.

Blueprint SYSTEM Annotation에서는:

### Calculation
카드 혜택 Rule 기반 deterministic calculation

### AI
복잡한 계산근거와 카드 Rule을 사용자가 이해하기 쉽게 설명

으로 역할을 분리한다.

---

# 27. 마지막 Apply 화면

신규카드 신청은 CardFit 내부에서 완료하지 않는다.

신규카드가 최종 조합에 포함된 경우 마지막 실행 화면에서만:

### C카드 신규 신청

카드사 공식 신청 페이지에서 직접 신청

**이동**

정도로 제공한다.

`발급받기`
같은 과도한 CTA는 사용하지 않는다.

CardFit은 신청서를 대신 작성하거나 제출하지 않는다.

---

# 28. 해지 Scope

CardFit은 기존 카드 해지:

- 상담
- 해지 신청
- 자동 해지
- 해지 대행

을 제공하지 않는다.

결과에서는:

`B카드 정리 검토`

와 같은 판단 정보는 제공할 수 있다.

실제 해지는 카드사 책임 영역이다.

---

# 29. Apply 화면 예시

### 이 조합을 적용하려면

#### A카드
**계속 사용**

CardFit의 결제 순서에 맞게 사용

---

#### B카드
**정리 검토**

필요하다면 카드사에서 직접 확인

---

#### C카드
**신규 신청**

카드사 공식 신청 페이지에서 직접 신청

`이동`

# 30. 정보 최신성 / 불확실성

카드 Rule과 약관은 변할 수 있다.

따라서 계산근거 화면에서:

- 적용 기준일
- 제외된 조건
- 확인되지 않은 비용

등을 표시한다.

예:

> 포인트 소멸, 자동납부 이전 등 일부 비용은 계산에 포함되지 않았습니다.

필수 정보가 없어서 정확히 계산할 수 없는 경우 임의로 숫자를 만들어내지 않는다.

# 36. Typography

현재까지 생성된 프로토타입에서 글씨가 지나치게 작았으므로 반드시 개선한다.

- 최소 폰트: 약 11px 이상
- 보조 설명: 11~13px
- Body: 13~15px
- Section title: 16~18px
- Main title: 20~24px
- Hero number: 30px 이상

정도로 설계한다.

작은 정보를 억지로 한 화면에 다 넣지 마라.

글자를 줄이는 대신:

- Accordion
- Bottom Sheet
- Details
- Progressive Disclosure
- 다음 화면

으로 정보를 이동시켜라.

# 37. Mobile Layout Rule

반드시 확인:

- 화면 너비를 넘는 텍스트 없음
- 가로 Overflow 없음
- 긴 금액이 영역을 깨지 않음
- 버튼 텍스트가 2줄 이상 이상하게 깨지지 않음
- Dynamic Island / Status Bar와 헤더가 겹치지 않음
- Fixed CTA와 본문이 겹치지 않음
- 모든 콘텐츠는 세로 스크롤 가능
- 한글 word-break 최적화
- Touch Target 충분히 확보

디자인은:

- Toss / Banksalad 수준의 현대적인 한국 핀테크 모바일 UI

- 중요한 숫자는 명확한 contrast

으로 한다.

# 40. 무엇을 하지 말아야 하는가

다음과 같은 결과물을 만들지 마라.

### 금지 1
카드 한 장 추천 서비스처럼 보이는 UX

### 금지 2
`이사·입주`, `결혼` 등을 카드혜택 계산 카테고리로 사용하는 UX

### 금지 3
미래지출 입력 시 할부기간까지 요구

### 금지 4
사용자가 모르는 발급일을 사전에 입력하도록 요구

### 금지 5
모든 정보를 한 화면에 몰아넣고 폰트를 작게 만드는 것

### 금지 6
`Net Benefit`, `Rule Engine` 등의 내부 용어를 사용자에게 그대로 노출

### 금지 7
미래지출을 입력하기도 전에 카드 유지/정리 결론을 표시

### 금지 8
Scenario 탭을 눌러도 숫자만 바뀌고 카드조합은 그대로인 fake logic

### 금지 9
CardFit 내부에서 카드신청 또는 해지를 대행하는 것

### 금지 10
GitHub의 비확정본을 제품 요구사항으로 사용하는 것

# 41. HTML 산출물 요구사항

하나의 standalone `.html` 파일로 만들어라.

외부 서버 없이 실행 가능해야 한다.

가능하면:

- HTML
- CSS
- Vanilla JavaScript

만 사용한다.

필요하다면 CDN 기반 Icon 정도는 사용할 수 있으나,
외부 Asset 의존도는 최소화한다.

# 42. 최종 산출물의 목적

이 Blueprint는 단순 개발 시안이 아니다.

PM / Designer / Developer / 발표 청중이 한눈에:

1. CardFit이 어떤 문제를 해결하는지
2. 사용자가 무엇을 입력하는지
3. 시스템이 무엇을 계산하는지
4. 왜 카드 1장이 아니라 카드 조합을 추천하는지
5. 왜 변경을 추천하거나 유지시키는지
6. 사용자가 실제 결제 시 어떻게 행동하는지
7. 추천 결과를 어떻게 검증할 수 있는지
8. 서비스가 어디까지 실행을 지원하는지

를 이해할 수 있어야 한다.

# 43. 최종 검수 Checklist

HTML을 완성한 뒤 스스로 다음을 검수하라.

- [ ] 추천의 단위가 끝까지 카드조합인가?
- [ ] 신규카드는 조합의 한 요소로만 표현되는가?
- [ ] 입력 카테고리가 실제 카드혜택 Rule과 연결 가능한가?
- [ ] Life Event를 소비 카테고리로 잘못 사용하지 않았는가?
- [ ] 미래 입력이 카테고리·금액·시점 정도로 단순한가?
- [ ] `예상대로`가 기본 Scenario인가?
- [ ] 적게/많이에서 카드조합도 달라질 수 있는가?
- [ ] 결과에서 예상 추가 혜택이 가장 먼저 보이는가?
- [ ] 카드 조합이 바로 이해되는가?
- [ ] 결제 순서가 실적 → 혜택한도 → 보조카드 구조인가?
- [ ] 특정 업종 혜택은 Exception으로 처리되는가?
- [ ] 계산근거를 금액으로 검증할 수 있는가?
- [ ] 사용자가 결과 화면에서 다른 단계로 건너뛸 수 있는가?
- [ ] 카드사 신청 링크는 마지막 Apply 단계에 있는가?
- [ ] 해지 대행을 제공하지 않는가?
- [ ] 작은 글씨 때문에 정보를 억지로 끼워넣지 않았는가?
- [ ] 402×874에서 Overflow가 없는가?
- [ ] 프로토타입의 입력 State와 결과 State가 실제로 연결되어 있는가?
- [ ] 제품 근거가 세 개의 `확정본` 폴더로만 제한되어 있는가?

위 조건을 모두 만족한 뒤 최종 HTML을 출력하라.
