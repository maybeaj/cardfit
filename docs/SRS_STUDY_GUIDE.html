01 · How to read

SRS는 무엇이고, PM에게 왜 중요한가

SRS(Software Requirements Specification)는 소프트웨어가 어떤 일을 해야 하는지, 어떤 조건을 지켜야 하는지, 무엇으로 “완료”를 판정할지 적는 계약서에 가깝습니다.

기능 요구사항 FR

시스템이 해야 하는 일

예: “미래 지출을 카테고리·금액·시점으로 입력할 수 있어야 한다.”

UI 요구사항 UI

사용자에게 어떻게 보여야 하는 일

예: 결과 화면에 배분표와 근거 화면으로 가는 CTA가 있어야 한다.

비기능 NFR

품질과 제약

예: 같은 입력은 같은 결과를 내고, 402×874 모바일에서 완주되어야 한다.

AC / Acceptance Criteria

완료 판정 기준

Given–When–Then으로 테스트 가능한 결과를 적는다.

PM의 핵심 질문“이 기능이 있나요?”보다 “어떤 입력에서, 어떤 결과가 나오면 완료인가요? 그 결과를 누가 어떻게 검증하나요?”가 더 좋은 질문입니다.
02 · Product logic

제품의 중심 흐름을 한 줄로 읽기

SRS의 FR 순서는 계산 순서이고, UI 화면의 경계와는 조금 다릅니다. 이 차이를 알면 “요구사항 9개 = 화면 9개”라는 오해를 피할 수 있습니다.

진단현재 카드 상태를 보여줌
미래 입력자동 제안값을 수정
시나리오적게·예상대로·많이
최적화조합 후보와 게이팅
배분카드별 역할과 금액
근거6항목 이상 공개
확정다음 행동과 경계 고지
제품의 정체성“무조건 더 좋은 카드를 추천”하는 서비스가 아니라, 바꿀 가치가 임계값을 넘을 때만 바꾸고, 그렇지 않으면 현재 조합 유지를 정상적인 성공 결과로 반환합니다.

Happy Path

정상 사용자가 입력하고 결과를 확인해 조합을 확정하는 주 흐름.

수정 루프

결과에서 입력으로 돌아가 지출을 고친 뒤 재계산하는 반복 흐름.

03 · Glossary / requirements

용어 해설집 ① — 요구사항과 우선순위

FR · Functional Requirement
기능 요구사항. 시스템이 수행해야 할 행동. “입력할 수 있어야 한다”, “계산해야 한다”처럼 동사로 읽습니다.
UI · User Interface Requirement
화면·상호작용 요구사항. 버튼, 배지, 화면 상태, CTA, 경계 문구처럼 사용자가 직접 경험하는 조건입니다.
NFR · Non-functional Requirement
비기능 요구사항. 기능의 내용보다 품질·보안·반응형·결정론성 등 “어떤 상태로 작동해야 하는가”를 말합니다.
MoSCoW
Must / Should / Could / Won’t의 우선순위 체계. “좋아 보이는 기능”을 모두 넣지 않도록 범위를 잠급니다.
Rationale
근거 또는 이유. 요구사항이 왜 존재하는지 설명하며, 우선순위 논쟁이 생겼을 때 판단 기준이 됩니다.
Scope / Out of Scope
이번에 하는 것과 하지 않는 것. “하지 않음”도 제품 전략과 일정 보호를 위한 명시적 결정입니다.
읽기 규칙Requirement → Input → Rule → Output → AC → Source → Priority 순서로 보면 “무엇을 받아 무엇을 계산하고 무엇을 보여주며 어떻게 검증하는가”가 한 번에 보입니다.
04 · Glossary / engineering

용어 해설집 ② — 엔지니어링 핵심어

Mock
실제 외부 시스템 대신 넣어둔 예시 데이터·가짜 구현. UX와 계산 흐름을 먼저 검증할 수 있지만, 실제 연동 가능성을 증명하지는 않습니다.
Rule Engine
혜택 규칙·임계값·제약을 코드로 일관되게 적용하는 계산 모듈. AI가 아니라 결정론적 로직이어야 합니다.
Deterministic · 결정론성
같은 입력을 주면 언제나 같은 결과가 나오는 성질. 금융 계산과 테스트의 신뢰 기반입니다.
Entity
업무에서 추적해야 하는 데이터 단위. 예: HeldCard, FutureSpendPlan, Calculation, PlanCandidate.
Schema
데이터의 구조와 필드 정의. 이름·타입·필수 여부·관계를 정해 코드와 데이터베이스가 같은 언어를 쓰게 합니다.
API Contract
입력 형식, 출력 형식, 오류 조건에 대한 약속. 실제 API가 없어도 계산 함수의 계약으로 먼저 정의할 수 있습니다.
State / 상태
객체나 화면이 현재 어떤 단계에 있는지. Loading, Empty, Success, 유지 결론처럼 상태마다 가능한 행동이 달라집니다.
Traceability
요구사항이 어떤 설계·코드·테스트와 연결되는지 추적하는 능력. 빠진 구현과 근거 없는 기능 추가를 발견합니다.
05 · Core calculation

FR-003: Net Benefit 게이팅 이해하기

CardFit의 가장 중요한 엔지니어링·제품 규칙입니다. 후보를 많이 만드는 것보다, 언제 추천하지 않을지를 명확히 하는 것이 핵심입니다.

Net Benefit = Gross Benefit − (연회비 + 실적 재적립 손실 + 발급 대기 비용)

변경 제안 조건: Net Benefit ≥ 50,000원 AND Net Benefit ≥ Gross Benefit × 15%
둘 다 충족

조합 변경안 반환

사용 카드 최대 2장, 신규 발급 최대 1장. 카드별 상태는 유지·해지·추가 중 하나입니다.

하나라도 미달

현재 조합 유지

실패가 아니라 정상 결과. “지금은 바꾸지 않아도 돼요”와 검토했던 대안을 함께 보여줍니다.

왜 절대값 AND 상대값인가?절대값만 보면 큰 혜택의 작은 개선을 과하게 권할 수 있고, 상대값만 보면 작은 금액 차이로 신규 발급을 권할 수 있습니다. 두 조건은 각각 다른 오판을 막습니다.

PM 확인: 50,000원과 15%는 실측값이 아니라 팀 합의 상수입니다. 운영 전환 시 실제 데이터로 재검증해야 합니다.

07 · UX & safety

화면 요구사항은 “예쁜 화면”이 아니라 통제 장치다

CardFit의 UI는 계산 결과를 꾸미는 층이 아니라, 잘못된 해석·규제 오인·근거 부족을 막는 제품 통제입니다.

진단 화면

미래 입력 전에는 절감액·추천 결과를 0건으로 유지합니다. 현재 상태만 보여줘야 합니다.

계산 화면

금액 산출과 설명은 결정론적 규칙 엔진·약관 기반 고정 템플릿으로 처리합니다. AI는 사용하지 않습니다.

근거 화면

실적구간·혜택한도·연회비·제외조건·기준일·미반영 항목을 공개합니다.

확정 화면

신규만 공식 페이지 아웃링크. 유지·해지는 직접 실행 버튼 없음. 신청·해지는 카드사에서 진행.

UX 용어: Progressive Disclosure사용자에게 한 번에 모든 기술 정보를 쏟지 않고, 결론 → 배분 → 근거 순서로 필요한 만큼 펼쳐 보이는 설계입니다. 투명성과 이해 가능성을 동시에 챙깁니다.

09 · Quality

NFR과 Acceptance Criteria는 어떻게 검증하는가

NFR-001

정확성

같은 입력을 3회 실행해 결과 불일치 0건. 배분 합계와 입력 총액 차이는 1원 이하.

NFR-002

보안

저장소·번들에 비밀키와 개인정보가 없어야 함. 커밋 전 스캔으로 확인.

NFR-003

반응형

모바일 402×874와 데스크톱에서 핵심 Happy Path를 완주.

Acceptance Criteria 읽는 법Given 사전 조건 → When 사용자 행동 → Then 기대 결과. “구현했다”가 아니라 “검증했다”를 말할 수 있는 형태입니다.

10 · Scope & technology

사용자가 덧붙인 C-TEC 제약을 어떻게 읽을까

아래 제약은 “배포 가능한 서비스”를 만들 때의 기술 방향입니다. 반면 현재 SRS 본문은 실제 백엔드·MyData 연동 없이 Mock과 standalone prototype을 전제로 합니다. 따라서 두 층위를 섞지 않는 것이 중요합니다.

제약뜻PM 관점의 확인 질문
C-TEC-001Next.js App Router 단일 풀스택프론트/백엔드 분리 없이 한 저장소에서 배포할 것인가?
C-TEC-002Server Actions / Route HandlersDB·외부 API 호출의 서버 경계와 권한 처리가 정의됐나?
C-TEC-003Prisma + 로컬 Supabase / 배포 Supabase로컬과 운영 DB의 스키마·마이그레이션 전략이 같은가?
C-TEC-004Tailwind CSS + shadcn/ui디자인 토큰과 컴포넌트 사용 규칙이 정해졌나?
C-TEC-005~006Vercel AI SDK, Gemini 기본·모델 교체 가능AI의 역할이 계산이 아닌 설명인지, 키가 서버에만 있는가?
C-TEC-007Vercel 단일 배포·Git Push 자동 배포환경 변수·preview·production 승인 흐름이 안전한가?
중요한 구분AI는 카드 혜택 금액을 계산하는 주체가 아닙니다. 금액과 게이팅은 결정론적 규칙 엔진, 설명 문장·요약은 필요할 때 AI로 분리해야 합니다. 이 경계를 SRS와 기술설계에 함께 기록하세요.

12 · Closing map

다음 학습 순서

한 번에 코드를 배우려고 하지 말고, SRS의 한 요구사항을 데이터·상태·테스트로 번역하는 연습부터 시작하세요. 아래 네 페이지가 실제 학습 내용입니다.

1단계

문서 구조 익히기

FR/UI/NFR/AC/Traceability를 구분하고, 각 항목의 책임을 설명합니다.

2단계

데이터 읽기

FutureSpendPlan → Calculation → PlanCandidate → Allocation 관계를 그려봅니다.

3단계

규칙과 상태 읽기

Net Benefit 식, 임계값, Empty·Loading·유지 결론을 테스트 케이스로 바꿉니다.

4단계

13 · Study 1 / requirements

학습 1 — 요구사항을 테스트 문장으로 바꾸기

목표는 용어를 외우는 것이 아니라, 모호한 기획 문장을 개발·QA가 실행할 수 있는 조건으로 바꾸는 것입니다.

학습할 개념Requirement, rationale, scope, priority, acceptance criteria, traceability
연습 단계실제로 해볼 일완료 기준
1. 동사 찾기FR-001에서 “입력할 수 있어야 한다”를 찾고 주어·행동·대상을 분리기능의 주체와 행동을 한 문장으로 설명
2. 조건 붙이기금액은 양수, 방향은 토글, 시점은 기준일+1~12개월로 정리정상·예외 입력을 각각 1개 이상 제시
3. Given–When–Then미래 지출 0건 → 계산 요청 → 결과를 반환하지 않음으로 작성다른 사람이 읽고 테스트 절차를 재현
4. 추적 연결FR-001 ↔ AC-001/007 ↔ 입력 화면 ↔ 테스트 Issue 연결요구사항 하나의 구현·검증 위치를 찾음
추천 실습새 기능을 하나 상상해 추가하지 말고, FR-001을 표 형식으로 다시 써보세요. “왜 필요한가?”와 “언제 실패인가?”가 비어 있으면 아직 운영 가능한 요구사항이 아닙니다.

15 · Study 3 / rules & tests

학습 3 — 규칙 엔진과 상태를 검증하기

CardFit에서 가장 중요한 학습 포인트입니다. 계산식이 맞는지뿐 아니라, 경계값과 “추천하지 않는 결과”까지 명확히 다뤄야 합니다.

예시: Gross Benefit = 120,000원
전환비용 = 30,000원
Net Benefit = 90,000원 → 50,000원 이상이고 Gross의 15% 이상이면 변경 제안
케이스기대 상태왜 중요한가
미래지출 0건Empty · 계산 차단미래 입력 없이 결과를 보여주지 않음
Net Benefit 49,999원현재 조합 유지절대 임계 경계값 검증
Net 60,000원, Gross 500,000원현재 조합 유지12%라 상대 임계 15% 미달
3개 시나리오 중 하나 실패부분 결과로 취급하지 않음불완전한 계산을 성공처럼 노출하지 않음
완료 기준정상 케이스 1개만 통과하는 것이 아니라, 경계값·빈 상태·근거 부족·유지 결론까지 테스트 케이스로 설명할 수 있어야 합니다. 이때부터 “규칙을 안다”고 말할 수 있습니다.
16 · Study 4 / web engineering

학습 4 — 기술 스택을 SRS에 연결하기

기술 이름을 먼저 외우기보다, SRS의 한 요구사항이 웹 애플리케이션의 어느 층에서 처리되는지 매핑해보세요.

학습 주제쉽게 말하면CardFit 연결 과제
Next.js App Router화면 경로와 서버 처리를 한 앱 안에서 구성진단·입력·결과 화면의 경계 그리기
Server Action / Route Handler브라우저가 서버에 작업을 요청하는 통로계산 요청과 근거 조회의 계약 작성
Prisma / PostgreSQL코드의 데이터 모델을 DB 구조로 연결HeldCard·Calculation 스키마 초안 만들기
Tailwind / shadcn/ui일관된 스타일과 재사용 UI 부품버튼·카드·상태 배지의 공통 규칙 정의
Vercel AI SDK / Gemini외부 AI를 서버 경계 안에서 호출계산과 설명의 책임 분리 문서화
Vercel 배포Git Push로 미리보기·운영 배포환경 변수와 운영 승인 체크리스트 작성
학습 순서HTML/CSS 기초 → JavaScript의 변수·함수·배열 → HTTP와 JSON → React 컴포넌트 → Next.js 서버/클라이언트 경계 → SQL/Prisma → 테스트·배포 순으로 진행하면 SRS와 연결하기 쉽습니다.
