## 1. 개요·목표

### 문제 정의

결혼·이사처럼 예정된 고액 지출을 앞둔 다장 카드 사용자는 과거 소비만 보는 비교 결과, 복잡한 실적·한도·연회비, 불투명한 추천 근거 때문에 앞으로의 결제 계획을 스스로 결정하기 어렵다.

| Pain | 현재 관찰·실패 지표 | 근거 등급 |
| --- | --- | --- |
| 과거 중심 추천 | 직접 확인한 경쟁 5곳 중 미래 소비 입력·조합 재설계·근거 공개를 동시에 제공한 곳 `0곳` | 🔵 `E-04` |
| 추천 근거 불신 | 자동대체 후 혜택 불일치 관련 민원 2022→2025년 `+88.4%` | 🔵 `E-02` |
| 복잡한 조건 | 수기 판단 약 `240분` | ⚪ 1인 진술 기반, 일반화 금지 |
| 미래 입력 부담 | 미래 입력 수고가 보상보다 클 수 있음 | 🟡 `A-01`, 실제 인터뷰 미완료 |

### 목표와 Desired Outcome

**결혼·이사처럼 예정된 고액 지출을 앞둔 다장 카드 사용자가, 사용자가 확인한 앞으로 12개월 지출 계획을 기준으로 현재 카드를 유지할지 더 유리한 조합으로 바꿀지와 결제 배분을 근거와 함께 5분 안에 결정하도록 돕는다.**

| ID | Desired Outcome | 프로토타입 판정 |
| --- | --- | --- |
| G1 | 수기 판단 대신 하나의 결론에 도달 | 온보딩→확정 Happy Path 완주 |
| G2 | 확인한 미래 계획을 계산에 100% 반영 | AC-001·010 |
| G3 | 바꿀 가치가 없으면 유지 반환률 100% | AC-004 |
| G4 | 결과당 근거 6항목 이상 공개 | AC-002 |
| G6 | 적게·예상대로·많이 3개 시나리오 모두 제공 | AC-005 |

## 2. 사용자와 페르소나

핵심 사용자는 **결혼·이사 등으로 앞으로의 지출이 과거와 달라질 예정이며 카드를 여러 장 보유한 사람**이다. 카드 1장만 쓰는 사용자와 법인카드 사용자는 이번 범위에서 제외한다.

| 여정 | Pain | Need | CardFit 대응 |
| --- | --- | --- | --- |
| 현재 상태 확인 | 과거 혜택 금액이 미래에도 맞는지 모름 | 기준 시점 구분 | 최근 12개월 기준임을 명시하고 미래 미반영 고지 |
| 미래 계획 입력 | 정확한 금액을 처음부터 쓰기 어려움 | 수정 가능한 출발점 | 과거 패턴 기반 제안 초안 |
| 조합 판단 | 실적·한도·연회비 계산이 복잡함 | 유지도 정답인 결론 | 결정론적 계산과 Net Benefit 게이팅 |
| 검증·확정 | 신규 발급 유도처럼 보임 | 계산 근거와 주도권 | 근거 6항목, 배분표, 직접 실행 경계 |

상세 타깃과 흐름은 [`SCOPE.md`](SCOPE.md) 2~3절을 따른다. Mock의 변경형·유지형 프로필은 내부 Fixture일 뿐이며 화면에서 페르소나를 선택시키거나 특정 인물 이름으로 체험시키지 않는다.

## 3. 사용자 스토리와 수용 기준

### US-01 미래 계획 반영

**As a** 앞으로 큰 지출이 예정된 다장 카드 사용자, **I want** 과거 패턴으로 제안된 지출을 확인·수정하고 싶다, **so that** 앞으로 쓸 돈을 기준으로 계산받을 수 있다.

- Given 제안값이 있는 상태, When 수정 없이 `이 계획대로 계산하기`, Then 화면의 전체 값이 앞으로 12개월 계획으로 확정되고 출처·확인 문구가 각각 표시된다(`AC-010`).
- Given 모든 항목을 삭제하거나 모두 0원인 상태, When 다음 단계 진입 시도, Then CTA가 비활성이고 결과는 `0건`이다(`AC-001`).
- Given 입력 흐름 진입, When 항목을 추가·수정·감소, Then 이벤트 필수 선택 단계와 처리 실패가 각각 `0건`이다(`AC-007`).

### US-02 안전한 조합 결정

**As a** 카드 조건을 직접 계산하기 어려운 사용자, **I want** 현재 조합을 유지할지 바꿀지 하나의 결론을 받고 싶다, **so that** 작은 이익 때문에 불필요한 카드를 만들지 않을 수 있다.

- Given Net Benefit이 5만원 미만 또는 Gross Benefit의 15% 미만, When 계산 완료, Then `현재 조합 유지` 반환률은 `100%`다(`AC-004`).
- Given 미래 계획 확정, When 계산 요청, Then 세 시나리오가 모두 선계산되고 기본 탭은 항상 `예상대로`다(`AC-005`).
- Given 변경 또는 유지 결론, When 결과 확인, Then 손익이 원 단위이고 비교 기준선이 누락된 결과는 `0건`이다(`AC-006`).

### US-03 근거 검증과 결제 배분

**As a** 추천을 그대로 믿기 어려운 사용자, **I want** 카드별 결제 금액과 적용 규칙을 확인하고 싶다, **so that** 결론을 스스로 검증할 수 있다.

- Given 결론 반환, When 결과 확인, Then 카드별 배분 합과 계획 총액 오차는 `≤1원`이다(`NFR-001`).
- Given 근거 화면 진입, When 근거 확인, Then 실적구간·혜택한도·연회비·제외조건·기준일·미반영 항목 `6개`가 표시되며 부족하면 결과를 거부한다(`AC-002`).
- Given 미반영 항목 존재, When 근거 확인, Then 출처 있는 상한만 `최대 ±n원`으로 표시되고 결론 차액 합산은 `0건`이다(`AC-002`).

### US-04 직접 확정과 실행 경계

**As a** 최종 결정권을 유지하고 싶은 사용자, **I want** 조합을 확정한 뒤 직접 할 행동과 서비스 경계를 알고 싶다, **so that** CardFit이 신청·해지를 대신한다고 오해하지 않는다.

- Given 근거 화면, When `이 조합 적용하기`, Then 확정 조합·카드별 다음 행동·경계 고지 3블록이 표시된다(`AC-008`).
- Given 해지 항목 포함, When 확정 화면 확인, Then 해지 실행 버튼은 `0개`이고 직접 진행 문구가 표시된다(`AC-003`).
- Given 신규 카드 포함, When 다음 행동 확인, Then 공식 카드사 아웃링크는 최대 `1개`이며 복귀 후 입력·조합·탭이 보존된다(`AC-008`, `FR-008`).

전체 Given/When/Then 정본은 [`SRS.md`](SRS.md) 8절이다.

## 4. 기능 요구사항

실측 Reach·Confidence가 없어 RICE 점수를 만들 수 없으므로 **MoSCoW**를 사용한다. 대안보다 가치가 높은 이유는 “미래라는 시간축”, “조합이라는 계산축”, “검증 가능한 근거” 세 가지다.

| 우선순위 | 요구사항 | 대안 대비 가치 |
| --- | --- | --- |
| Must | FR-001 미래지출 입력 | 과거 기준 비교에 없는 시간축의 진입점 |
| Must | FR-002 3개 시나리오 계산 | 예측 오차를 적게·예상대로·많이로 흡수 |
| Must | FR-003 조합 최적화·게이팅 | 단일 카드 순위 대신 유지도 포함한 조합 결론 |
| Must | FR-004 결제수단 배분 | 추천 카드 목록이 아니라 실제 결제 계획 제공 |
| Must | FR-005 근거 6항목 공개 | 결과 금액만 보여주는 비교의 불신 완화 |
| Must | FR-006 초기값 자동 제안 | 최대 가정 A-01의 입력 부담 완화 |
| Should | FR-007 이벤트 비종속 입력 | 결혼·이사 이름을 고르지 않아도 증감 입력 가능 |
| Should | FR-008 조합 확정·경계 고지 | 주도권을 사용자에게 남기고 대행 오인 차단 |
| Could/Backlog | 단계적 전환, 소득·지출 범위 입력 | 핵심 결론 검증 후 필요성 판단 |
| Won't v0.1 | 실 마이데이터, 해지·신청 대행, 실결제, 인증, 30일 완주 계측, 정기 재진단 | 32시간 Mock 프로토타입의 목적·권한·시간축 밖 |

## 5. 비기능 요구사항

운영 서비스용 목표를 프로토타입의 사실처럼 쓰지 않는다. 참고 저장소의 `p95 ≤5s`, 가용성 `99.5%`, 오류율 `0.1%`는 실서비스 초안이며 현재 합격 기준으로 승계하지 않는다.

| 영역 | v0.1 요구사항 | 판정 |
| --- | --- | --- |
| 성능 | 별도 API가 없는 클라이언트 계산이므로 p95 응답 목표는 **미설정**. E2에서 결론 도달시간 기준선을 먼저 수집 | 이번에는 자동 테스트 시간 기록만 보존 |
| 정확성 | 같은 입력 3회 결과 불일치 `0건`, 배분 합 오차 `≤1원` | `NFR-001`·Vitest |
| 신뢰성 | 월 가용성은 **해당 없음**. 정적 프로토타입이므로 네트워크 복구를 구현하지 않음 | Happy Path E2E 2종 통과 |
| 보안·비용 | 개인정보·비밀키·유료 외부 API `0개`; 런타임 외부 API 비용 `0원` | 저장소·번들 정적 스캔 |
| 반응형 | 402×874와 1440×900에서 핵심 흐름 유지 | `NFR-003`·Playwright |
| 모니터링 | 운영 대시보드·알림은 범위 밖. 테스트 로그, 콘솔 오류, AC/Guardrail 결과를 검증 증거로 보존 | 콘솔 오류 `0건`, P0 테스트 전부 통과 |

실서비스 전에는 실제 트래픽으로 p95·가용성·비용 기준선을 수집하고 별도 SLO를 승인해야 한다.

## 8. 실험·롤아웃·측정

| 단계 | 가설·채널 | 측정 | 성공·중단 기준 |
| --- | --- | --- | --- |
| v0.1 내부 프로토타입 | Fixture 2종으로 실제 흐름과 안전장치 검증 | AC·NFR·Guardrail | P0 전부 통과, 과잉 추천·근거 누락·오인 문구 각 0건 |
| E1 문제 인터뷰 | 결혼·이사 예정 실제 사용자 `n=15` | 미래 변화 입력 Job 자발 언급률 | `≥60%` 🟡; 미달 시 문제 정의 재검토 |
| E2 Concierge | 제휴 모집 40명, 유효 30명; 사람이 같은 계산 제공 | 결론 수용률, 신뢰 전후 변화, 유지 제외군 비율 | 기준 `≥40%`, `<20%`면 A-01 피벗 🟡 |
| E3 초기값 A/B | E2 통과 후 `n=500` | 온보딩 완료율, 수정률, 재계산률 | 완료율 `≥60%` 및 대조군 대비 `+15%p` 🟡 |
| 한정 베타 | 실연동·법률·보안 검토 완료 채널 | 결론 수용률, 오류, 근거 누락, 비용 | Guardrail 1건이면 중단 |

경쟁 벤치마크는 동일한 소비 스냅샷 `n=20`을 사용해 미래 반영 여부, 조합 재설계 여부, 공개 근거 항목 수를 비교한다. 현재 관찰은 직접 확인한 5곳으로만 한정하며 “시장 전체”로 일반화하지 않는다.

사용성 테스트를 실행하지 못한 현재는 Fixture 시뮬레이션으로 **계산 분기와 UX 완주 가능성만** 검증한다. 결론 수용률이나 신뢰 상승을 시뮬레이션 결과로 주장하지 않는다.
